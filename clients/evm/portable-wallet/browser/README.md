# Browser wallet

Open the [P2PARTY wallet](https://p2party.github.io/p2party-server/restore/). It uses valueless Testnet 1 units.

- [Create a wallet](https://p2party.github.io/p2party-server/restore/#create) to make a private encrypted **.jwe backup** and a separate **P2W1- recovery code**. Download the file, store the code separately, then check both in the wallet before sharing your first payment request. There is no seed phrase.
- [Restore a wallet](https://p2party.github.io/p2party-server/restore/#restore) by selecting or dropping your latest .jwe file, or pasting its encrypted contents. Enter its recovery code to see the reported balance, source and block height.
- [Receive a payment](https://p2party.github.io/p2party-server/restore/#receive) by sharing a **public one-use request** as text, a JSON file or a QR code. Keep the .jwe file and recovery code private. The sender can pay while your browser is closed.
- [Check your balance](https://p2party.github.io/p2party-server/restore/#balance) after returning. Choose **Check for payments** in the hosted wallet to check for newer activity. A downloaded offline wallet can import a snapshot file from a replica you trust. The amount covers the requests in the backup you opened.
- To change browsers, open **Move this wallet to another browser** and download the encrypted backup. On the other browser, choose **Restore a wallet** and enter your original recovery code with that file. Adding a receive request creates a new key and a new backup revision. Take the updated file across before expecting the new request to appear there. If both devices added requests independently, keep both files.

The browser supports the companion’s ML-DSA-65 and SLH-DSA-SHA2-192s backups. Every key and nonce must reopen its original full commitment before the browser accepts the wallet. [Wallet backup and native transfer format](../README.md)

If your earlier wallet is one receive folder containing `key.pk8` and the raw `nonce`, open **Import an older command-line wallet**. Select both files and enter the original full public receive commitment. The browser checks the opening locally, creates an encrypted kit for that request and gives you a new recovery code to keep separately. Each folder represents one receive request. For several original folders the desktop converter can collect them in one checked backup. [Multi-folder converter](../README.md#bring-an-existing-key-and-receive-nonce)

To use the tool offline, open the released HTML file in a browser with Web Crypto. Save a verified copy before disconnecting. The app includes its own scripts, styles and favicon. Its CSP pins inline script and style hashes and blocks network connections. The tool accepts public JSON transfer requests following the companion's format. Review the whole amount, full recipient commitment, suite, input and expiry before signing. Anyone with the resulting signed file can submit that payment. Current chain state and final acceptance require a verified validator. [Download the HTML](restore-wallet.html) · [SHA-256 checksum](restore-wallet.html.sha256)

**Remember encrypted backup** is optional and initially off. On explicit selection the tool stores only the authenticated compact JWE ciphertext, even if the pasted text wrapped the ciphertext in a larger JSON object. The next visit can reopen it with the separate code. Browser storage is shared across paths on the same origin and may be unavailable or cleared. Keep the original backup and code separately. **Forget** removes the browser's stored copy. The application does not send either secret to a server. Reloading, navigating away or locking discards the active signer. The browser or operating system controls memory reclamation. Anyone controlling your device, installed extensions or served application could compromise an unlocked wallet.

The browser and companion share the JWE envelope checks and public payment request validation. The browser uses the pinned JOSE implementation with Web Crypto AES-256-GCM and uses the published ledger client for native wire encoding. Its strict PKCS#8 reader supports standard ML-DSA seed, expanded and verified combined representations. It recomputes the SLH public root from the encoded seeds. The post-quantum signer uses Noble’s randomized signing and checks every resulting signature with the derived public key. The library documents a self-review and the timing limitations of JavaScript. An independent wallet or signer audit is pending. [M. Jones and J. Hildebrand, RFC 7516 (2015)](https://www.rfc-editor.org/rfc/rfc7516) · [RFC 9881 §5, ML-DSA private keys](https://www.rfc-editor.org/rfc/rfc9881.html#section-5) · [RFC 9909 §5, SLH-DSA private keys](https://www.rfc-editor.org/rfc/rfc9909.html#section-5) · [Noble security notes](https://github.com/paulmillr/noble-post-quantum/tree/0.7.1#security)

## Receive a payment, including while offline

1. Create a wallet or open the latest backed-up wallet. Select a fresh receive request using ML-DSA-65 or SLH-DSA-SHA2-192s. The browser generates an independent signing key and nonce for each request.
2. Download the updated encrypted file and keep the recovery code separately. Adding a request to an existing wallet reuses its original code. Select the actual downloaded file and enter the code from your saved copy to check it. Only then can the browser display the request.
3. Send the payer the **public one-unit request** as text, a JSON file or its locally generated QR code. It contains the Testnet 1 chain and genesis identifiers, one test unit of weight, recipient suite and full commitment. Anyone can see that request's public transaction history. No signing key, nonce, recovery code or list of your other requests is included. A Testnet 1 commitment can receive a unit only once; prepare a fresh request for each payer.
4. The sender can pay while your browser is closed. Restore the **latest file** and refresh the wallet against the validator when you reconnect. The browser checks all backed-up commitments locally against the verified public history; the validator receives no per-address lookup. A received unit can be selected locally as an input for a new payment after a successful verification. A unit received and subsequently spent from another copy still appears as spent. Each status is tied to a checked height. An interrupted check leaves the last observation in place. An unspent-only imported file can report a matching current unit; absence there cannot distinguish an already spent unit from one never received.
5. Carry the updated backup to other browsers. An older backup cannot derive a later independently generated key or nonce. Use one device at a time for creating new requests and keep previously saved versions if two devices created different requests independently.

The public JSON envelope has type `p2party.payment-request`, version `1`, a pinned native chain and genesis, `weight: "0x1"` and `recipient: {suite, commitment}`. Its recipient is the native ledger client's descriptor. A sender can compose an ordinary native payment from a verified owned unspent unit (or the complete native unit supplied by a trusted client), the request and a chosen finite expiry. Review before signing. Broadcasting the signed wire and obtaining acceptance are separate actions. [Request parser and QR encoder](receive.mjs) · [Native client and RPC](../../README.md#sign-a-transfer-locally)

## Balance in the wallet and site navigation

After restore, the wallet shows the reported available amount for all receive commitments in that backup. Open **Account** to access your balance or receive a payment. Its initial observation comes from the embedded public Testnet 1 checkpoint at **height 3, November 27, 2026 at 15:54:08 UTC**. Open the balance to check its height, source and observation time. A confirmed zero at that height is different from an unavailable report. A backup covering fewer receive requests can report less than the holder owns.

**Refresh balance** opens the first-party public snapshot page and asks the public validator for the same complete dataset everyone receives. The signer sends no address, receive commitment, portfolio or signing credential to that page. It verifies each native transfer since the pinned height with the appropriate post-quantum signature, original input opening, unit weight, inclusive expiry, unique destination and unspent input. It then compares the entire reconstructed 128-unit state with the published snapshot. A competing snapshot at the same height or one older than the last observation is rejected. The valid history and the head the single sequencer chose to publish establish the result; they cannot establish that the operator has never signed a competing history or withheld a newer tip. An incomplete or failed refresh keeps the last amount and marks it as last known. A refresh pins the reported target height and its last move ID, verifies pages of up to 32 receipts, then checks the complete 128-unit snapshot before displaying updated results. Flow-control acknowledgements contain only a temporary stream nonce and a public verified height. The wallet can traverse more than 256 receipts in one refresh; it keeps replay state, including used commitments, locally for the duration. Locking or interrupting the operation discards incomplete results. [Embedded public checkpoint](balance-checkpoint.json) · [Native verification rules](public-ledger.mjs)

A downloaded wallet can also import a complete replica snapshot file offline. The signer checks its chain identity, structure, unit count and suite/commitment matching. The reported holdings still depend on the chosen replica. The import records the amount as a file report separate from a native-signature-checked refresh. [Replica snapshot export](../README.md#check-the-wallet-total-privately)

Only a balance from the shipped checkpoint or a successful live receipt replay is eligible for website display. An imported file stays private. After a failed or conflicting check, refresh successfully before sharing. The total stays in the wallet unless you choose **Show total on p2party.com**. The destination site asks whether to place that observed amount and height in its navbar. The two windows exchange only a one-time challenge, the decimal amount and block height; the site will learn this aggregate if you choose to share. The source and recipient check each other's exact origin and window. Refresh and website display require an explicitly opened popup in the hosted signer; the disconnected copy remains usable for offline imports and signing.

## Rebuild a release

Use Node 26.13.1 or later and run the following in the parent `portable-wallet` directory. The committed lockfile pins the published native ledger client, Noble, JOSE and the build tool. The build writes one standalone HTML file and its SHA-256 digest. A clean rebuild should reproduce the checked-in bytes.

```sh
npm ci
npm run build:browser
git diff --exit-code -- browser/restore-wallet.html browser/restore-wallet.html.sha256
P2PARTY_WALLET_VERIFIER=/absolute/path/to/demos-ledger-verify npm test
```

The browser integration test exercises the release HTML in Chromium and Firefox with generated, valueless fixtures. Install Playwright and its two browser engines in a separate test environment. To use a previous published companion as the archive producer, set `P2PARTY_ARCHIVE_WRITER` to its local wallet.mjs module. The verifier checks the signed bytes exported through the user interface.

```sh
PLAYWRIGHT_MODULE=/absolute/path/to/node_modules/playwright \
P2PARTY_WALLET_VERIFIER=/absolute/path/to/demos-ledger-verify \
node --test browser/standalone.test.mjs browser/receive-browser.test.mjs
```

The receiving test takes a wallet backup actually downloaded in Chromium, pastes its contents into Firefox, and checks the same request and historical balance there. Separate ephemeral payer and receiver profiles exercise offline receipt. It creates a browser-only kit, checks a downloaded backup, decodes the public QR, signs a one-unit transfer with a disposable funded test fixture, then restores a previously disconnected receiver and recognizes the credit after verification. The included core tests also reconcile 257 subsequent receipts and identify a receipt spent from another device before the restoring wallet came back online. Public network state and balances remain untouched by these tests.

For release hosting, publish the same pristine bytes as the directory index and its `restore-wallet.html` sibling so the download link always returns the original release. Use trusted HTTPS hosting, or distribute the standalone file through a trusted channel. An HTML file can be checked offline with its trusted digest. A hash embedded in a page cannot authenticate the server delivering the page.
